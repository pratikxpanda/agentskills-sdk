## 1. `agentskills` CLI

**Labels:** `theme:dx`, `type:feature`, `package:cli`

> **Status: implemented.** Both open questions were resolved toward the dependency-light
> answer; see the implementation notes.

### Problem

There is no way to work with a skill without writing Python. Validation only happens inside
`registry.register()`, at runtime, in someone's application — so a malformed `SKILL.md` is
discovered by an agent failing to start rather than by the author who wrote it. Authoring a new
skill means copying an existing folder and hoping the frontmatter is right.

### Proposal

A new `agentskills-cli` package exposing an `agentskills` entry point.

| Command | Behaviour |
|---|---|
| `agentskills init <name>` | Scaffold `SKILL.md` with valid frontmatter plus empty `references/`, `scripts/`, `assets/` folders. |
| `agentskills validate <path>` | Run `validate_skill()` against one skill or a directory of them. Human-readable output by default, `--format json` for machines. **Exit non-zero on failure** — this is the contract CI depends on. |
| `agentskills lint <path>` | Non-fatal quality warnings: description too long for a catalog, body over a token budget, resources present but never referenced from the body, missing `version`. |
| `agentskills inspect <path>` | Render what an agent would actually see — the catalog entry, the metadata, the body — so authors can check token cost before shipping. |
| `agentskills serve <path>` | Run the MCP server over a folder of skills without hand-writing a `server.json`. |

Keep the dependency footprint small; the CLI should install without pulling in any framework
integration.

### Open questions

- Separate package, or an extra on `agentskills-core` (`pip install agentskills-core[cli]`)? A separate package keeps core dependency-light, which is a stated product principle.
- Which argument parser — stdlib `argparse` (no dependency) or `typer`/`click` (nicer UX, extra dependency)?

### Acceptance criteria

- [x] All five commands implemented with `--help`
- [x] `validate` exits non-zero on any failure and zero on success
- [x] `validate` handles both a single skill folder and a directory of skills
- [x] `--format json` output is stable and documented
- [x] Installs without any framework integration dependency
- [x] Package README with examples

### Implementation notes

**Both open questions were answered the same way, for the same reason.** A separate
`agentskills-cli` package rather than `agentskills-core[cli]`, and stdlib `argparse` rather
than `click` or `typer`. Item 2 installs this CLI into other people's CI, so every dependency
it carries is a supply-chain edge those repositories inherit for the privilege of checking a
markdown file. `argparse` costs some polish in `--help`; that is the whole price.

The MCP server is an optional `serve` extra for the same reason: `mcp` and `pydantic` have no
business being installed by a job that only runs `validate`.

**The forgiving parser was the actual problem worth solving.**
`split_frontmatter()` returns `({}, raw)` on a YAML error rather than raising — a
deliberate choice in core, since a provider should not explode on one bad skill. But it means
a mistyped colon arrives at `validate_skill()` as "metadata missing required 'name'" and
"metadata missing required 'description'", which tells an author nothing about what is wrong.
The CLI therefore parses the frontmatter itself first and reports the real cause: missing
delimiter, unclosed block, oversized block, invalid YAML, or a sequence where a mapping
belongs. Spec checks are skipped when that fails, because they can only restate the damage.

This is also where line numbers come from. `problem_mark.line + 1` maps a YAML error back to
a `SKILL.md` line, which is exactly what item 2 needs to annotate a pull request diff inline —
without it the Action can only annotate at file level.

**Exit code 2 exists to keep "found a problem" apart from "could not look".** A missing path,
an uninstalled extra, and an unwritable directory all exit 2; broken skills exit 1. A workflow
that collapses every non-zero into "invalid skill" reports a typo in a path as a spec
violation, and the author goes looking for a fault in a file that is fine.

**The scaffold is validated before it is written.** `init` builds an in-memory provider over
the template and runs the real `validate_skill()` against it. That rejects `init "Bad Name"`
without copying `_NAME_RE` into this package, and it means the template we ship cannot quietly
drift out of conformance — if the spec tightens, `init` starts failing its own output.

**Lint thresholds are opinions, so they are named and adjustable.** `--max-body-tokens` is a
flag; the 500-character catalog description ceiling is a constant with the reasoning attached
(a catalog entry is charged on every turn, a body only when loaded). Token counts are
`len(text) / 4`, which is honest enough to flag an outlier and nowhere near a real tokenizer.

### Observations for later

**`lint` cannot warn about unknown frontmatter keys.** Core recognises exactly seven, warns
about anything else at registration, and keeps that set in a private `_KNOWN_KEYS`. Surfacing
it here would mean duplicating the constant in a second package — the drift trap already on
the follow-ups list. Core should export the known-key set; until it does, this lint is absent
rather than wrong.

**A seventh package must be registered in seven places** — root `pyproject.toml` three times
(path dependency, `source_pkgs`, isort first-party), `COVERAGE_FLOORS`, both bump scripts,
`check_release_version.py`, and `publish.yml` twice (build loop and publish step). Only the
last one fails silently: everything else errors, but a package missing from `publish.yml`
simply never ships. Recorded in `.github/copilot-instructions.md`.

**`agentskills-cli` is a new PyPI project**, so it needs a pending trusted publisher registered
before the v0.4.0 tag — and the pending-publisher uniqueness limit documented in item 12 means
it cannot be registered alongside another pending one.

## 2. Skill validation GitHub Action

**Labels:** `theme:dx`, `type:feature`

**Depends on:** item 1 (CLI)

> **Status: implemented.** Annotations are emitted by the CLI itself as
> `--format github`, so the action stays a composite wrapper with no logic of its own; see the
> implementation notes.

### Problem

Anyone maintaining a repository of skills has no way to catch a broken `SKILL.md` before it
reaches consumers.

### Proposal

A composite GitHub Action wrapping `agentskills validate`, published so skill repositories can
gate their PRs:

```yaml
- uses: pratikxpanda/agentskills-sdk/actions/validate@v1
  with:
    path: ./skills
    fail-on-lint: false
```

Annotate failures on the offending lines via workflow commands so they surface in the PR diff
rather than only in the log.

This is the highest-leverage adoption item on the roadmap — it puts the SDK into other
people's CI, where it gets seen by everyone who opens a PR against those repos.

### Acceptance criteria

- [x] Action validates a directory of skills and fails the check on invalid input
- [x] Failures annotated inline on the PR
- [x] `fail-on-lint` toggles whether lint warnings break the build
- [x] Documented in the root README with a copy-pasteable snippet
- [x] Dogfooded on this repo's own `examples/skills/`

### Implementation notes

**The annotations are a CLI output format, not a script inside the action.** `--format github`
sits beside `--format text` and `--format json`, which is where every other linter puts it. The
alternative was a Python script in `actions/validate/` parsing the JSON contract — a second
implementation of the finding model, living outside `packages/`, where neither the coverage floor
nor `ruff` reaches. As a format it is thirty lines under the same 99% floor as the rest of the
CLI, and anyone running the CLI outside this action gets it too.

**The action is a composite wrapper and deliberately thin.** It installs the CLI, runs two
commands, and has no logic of its own beyond assembling arguments. Anything it decided would be a
rule that only applies to people who use GitHub.

**Lint runs only after `validate` passes.** `lint_location()` reports unparseable frontmatter as
an error rather than guessing, so on a broken skill both commands annotate the same line with the
same message. Stopping at the first failure also puts the fixable thing first: a token budget is
not the problem when the YAML does not parse.

**An `agentskills` already on `PATH` is used as-is.** Otherwise the action would silently replace
a repository's pinned CLI with the latest release, which makes the action — not the repository —
the thing that decides which rules apply. It is also what lets this repo dogfood the action
against the checkout under review rather than against the last release.

**Inputs reach the shell as environment variables, never through `${{ }}`.** An expression
interpolated into a `run:` block is evaluated before bash sees it, so anything an attacker can put
in the triggering event becomes shell source. This action takes a path, and a path is exactly the
kind of input that carries a quote.

### Observations for later

**`--format github` has no equivalent for other CI systems.** GitLab, Azure Pipelines, and
Buildkite all have annotation formats. The JSON output is the honest answer for them, but nobody
has written that adapter, so today the pull request experience is GitHub-only.

**The action cannot be tagged until the CLI is on PyPI.** `pratikxpanda/agentskills-sdk/actions/validate@v1`
needs a `v1` tag, and the action installs `agentskills-cli`, which does not exist on the index
until v0.4.0 ships. The README snippet is correct and will not work until then.

**Nothing verifies the action's failure path in CI.** The dogfood job proves a valid skill
passes. A fixture that is deliberately broken would need `continue-on-error` and a step asserting
the outcome, which is a second workflow's worth of machinery to test one bash line.

## 3. Provider conformance test kit

**Labels:** `theme:correctness`, `type:feature`, `package:testing`

### Problem

`SkillProvider` is an informal contract. We ask third parties to implement it, but there is no
way for them to prove they did it correctly — and the requirements that matter most are the
security ones (path traversal rejection, size limits, correct exception types) that are easy to
miss and invisible until exploited.

### Proposal

A new `agentskills-testing` package publishing a reusable pytest suite:

```python
from agentskills_testing import ProviderConformanceSuite

class TestMyProvider(ProviderConformanceSuite):
    @pytest.fixture
    def provider(self):
        return MyProvider(...)
```

The suite asserts the behaviours a provider must exhibit:

- `SkillNotFoundError` for unknown skill IDs
- `ResourceNotFoundError` for unknown resources
- Rejection of traversal-style identifiers (`../`, absolute paths, encoded variants)
- Size limits enforced
- `get_metadata()` / `get_body()` agree with each other for the same `SKILL.md`
- Every method is genuinely awaitable and does not block the event loop
- `list_resources()` behaviour once that lands

Requires a documented fixture contract describing the skill layout a provider under test must
expose. Run it against the built-in `fs` and `http` providers to prove the suite is real.

### Acceptance criteria

- [x] Suite published as `agentskills-testing` and importable
- [x] Passes against both built-in providers
- [x] Deliberately broken provider fixtures fail the expected assertions
- [x] Security assertions (traversal, size limits) included and non-skippable
- [x] Documented in the custom-provider section of the root README

> **Implemented, awaiting release.** Shipped as `packages/testing/agentskills-testing`,
> alongside item 4 on one branch — item 4's first criterion is "passes the conformance suite from
> item 3", so splitting them would have produced a branch that could not verify itself.

### Implementation notes

**The suite found a real bug on its first run against both providers.** `agentskills-http` raised
a plain `ValueError` for a traversal-shaped `skill_id` or resource name, where `agentskills-fs`
raised `SkillNotFoundError` / `ResourceNotFoundError`. `ValueError` is not an `AgentSkillsError`,
so a consumer could not write provider-agnostic error handling — the one thing the ABC exists to
make possible. `_validate_identifier` now takes the exception type its caller documents, and
raises what the ABC's `Raises:` clauses promise. Five assertions in `test_static.py` changed with
it; the constructor's `ValueError`s (bad `max_retries`, `http://` under `require_tls`) are
untouched, because those are programmer errors at construction time, not lookup failures.

**Then it found a second one, and only on Linux.** `agentskills-fs` leaked
`ValueError: embedded null character in path` for an identifier containing a NUL byte. A NUL
truncates a path in the C layer, and the platforms disagree about it: POSIX `realpath` calls
`lstat`, which rejects it, while Windows resolves the string and the existing
`is_relative_to(root)` check catches it. The suite passed locally and failed in CI on Python
3.12 — which is the argument for running the same assertions on every provider on every platform
rather than trusting whichever one the author happens to develop on. Both `_skill_dir` and
`_read_subdir_file_sync` now refuse a NUL explicitly, before `resolve()` sees it, so the
behaviour no longer depends on the operating system.

**Size limits are not part of the universal contract.** An in-memory provider has no external
source to bound, and asserting a filesystem's constraints against a dict would have forced either
a skip (which the acceptance criteria forbid) or a pointless `max_bytes` parameter on a data
structure. They live in a separate, opt-in `ContentLimitConformanceSuite` requiring a
`limited_provider` fixture, documented as required for any provider reading bytes it did not
author. `fs` and `http` run both suites; the in-memory provider runs the base suite only. The
traversal assertions stay in the base suite and are not skippable.

**Every async test method carries an explicit `@pytest.mark.asyncio`.** This repo runs
`asyncio_mode = "auto"`; a consumer's repo may run `strict`. A kit that only collects under one
project's configuration is not a kit.

**The suite asserts three things the ABC did not previously state**, so the ABC now states them:
metadata must not be shared mutable state between calls (a provider caching a parsed dict and
returning it lets one caller corrupt another's), repeated reads must agree (a provider streaming
without buffering passes the first read and returns empty on the second), and resource getters
must return `bytes` rather than `str` (decoding on the way out makes a PNG unreachable). Only the
first needed a docstring change in `agentskills-core`.

**Twelve deliberately broken providers prove the suite bites.** `tests/test_conformance.py`
subclasses `InMemorySkillProvider` once per contract clause — swallowing a missing skill,
resolving traversal, inlining the body into metadata, sharing a metadata dict, advertising a
listing capability it then refuses, decoding resources, reading once — and asserts the matching
suite method rejects each. A kit nobody has watched fail has unknown coverage.

**`pytest --cov` cannot see a package that registers a pytest11 entry point.** Entry-point plugins
are imported before pytest-cov starts measuring, so `agentskills_testing` *and* `agentskills_core`
came back at 0% and the aggregate dropped from 97% to 86%. `scripts/dev.py test:cov` now runs
`coverage run -m pytest`, which starts coverage before pytest loads anything. Aggregate is 98%.

**The HTTP conformance run took 26 seconds before a module-scoped `httpx.AsyncClient`.** Each
`HTTPStaticFileSkillProvider(...)` builds a TLS context (~0.17s) and the suite has fifty tests.
respx intercepts before the client touches a socket, so it never binds to an event loop and is
safe to share. 26s → 0.4s.

### Observations for later

- **The rest of `agentskills-http`'s own test suite is slow for the same reason** — every test
  constructs a provider, and therefore a TLS context. The full run is ~70s, most of it there. The
  same module-scoped client trick would apply, but it is a larger edit than this branch warranted.
- **`agentskills-core`'s own tests still use `AsyncMock(spec=SkillProvider)`** and cannot use
  `InMemorySkillProvider` without a circular dependency. Those mocks have the same defect as the
  ones replaced here — resource getters that raise `KeyError` instead of `ResourceNotFoundError` —
  so core is tested against a provider that does not conform. Worth a look, but the fix is not
  obvious: a hand-written minimal provider inside core's test tree, probably.
- **`agentskills-testing` is a new PyPI project.** It needs a pending trusted publisher registered
  before the v0.4.0 tag, and only one pending publisher can exist at a time across identically
  claimed distributions — so it and `agentskills-cli` must be bootstrapped in sequence.
- **The conformance fixture contract is a compatibility surface.** Adding an assertion that needs
  new fixture content is a breaking change for anyone already using the suite. Worth an explicit
  policy before 1.0.

## 4. Test doubles for downstream users

**Labels:** `theme:dx`, `type:feature`, `package:testing`, `good-first-issue`

### Problem

Anyone writing tests for an agent that consumes skills has to hand-roll an `AsyncMock` of
`SkillProvider` — as this repo's own test suites do, duplicating `_mock_provider` across
integration packages.

### Proposal

Ship in `agentskills-testing`:

- `InMemorySkillProvider(skills: dict)` — a real, spec-compliant provider backed by a dict, no disk or network.
- pytest fixtures for a populated registry and a single sample skill.
- A `build_skill(...)` helper for constructing valid `SKILL.md` content in tests.

Then replace the duplicated `_mock_provider` helpers in this repo's integration tests with it.

### Acceptance criteria

- [x] `InMemorySkillProvider` passes the conformance suite from item 3
- [x] Fixtures documented with examples
- [x] This repo's integration tests use it instead of local mocks

> **Implemented, awaiting release.** Shipped with item 3 on the same branch.

### Implementation notes

**The four duplicated `_mock_provider` helpers kept their signatures.** Only the body changed, from
building an `AsyncMock(spec=SkillProvider)` to building an `InMemorySkillProvider`, so ~160
existing call sites needed no edit and the diff stays reviewable.

**Three tests had been reaching into the mock rather than describing a scenario**, and all three
got shorter. `provider.list_resources.side_effect = ResourceListingNotSupportedError(...)` became
`InMemorySkillProvider(..., supports_resource_listing=False)`. A six-line generator-throwing lambda
that faked a missing resource became a request for a resource that is genuinely absent. Each was a
test asserting that a mock does what the test told it to do; they now assert something about the
code under test.

**`InMemorySkillProvider` accepts a bare string as a skill's body**, which covers the common case
where the content does not matter, and `build_skill()` produces frontmatter that passes
`validate_skill()`, so a test that does not care about metadata does not have to invent any.

**The fixtures ship as a `pytest11` entry point**, so installing the package makes
`sample_skill`, `skill_provider`, and `skill_registry` available with no import and no
`conftest.py` entry. The async one is decorated `@pytest_asyncio.fixture` so it resolves under
strict mode as well as auto. This convenience is what broke coverage measurement — see item 3.

### Observations for later

- **The old mocks were not spec-compliant**, and had not been for as long as they existed: their
  resource getters used `side_effect = lambda sid, name: mapping[name]`, which raises `KeyError`
  rather than `ResourceNotFoundError`. Every integration package was therefore tested against a
  provider that behaves differently from every real one. Nothing broke, but nothing would have
  caught it either. This is the argument for the conformance suite in miniature.
- **`render_skill_md()` is currently used only by the fs conformance fixture.** If a second caller
  never appears, consider whether it belongs in the public API.

## 5. Registry-level skill discovery

**Labels:** `theme:dx`, `type:feature`, `package:core`, `package:fs`, `package:http`

### Problem

`registry.register(skill_id, provider)` requires knowing every skill ID up front. Pointing at a
folder of thirty skills means hard-coding thirty identifiers, and adding a skill means editing
application code.

### Proposal

Optional `discover()` on `SkillProvider` returning available skill IDs, plus:

```python
await registry.register_all(provider)
```

- **Filesystem:** enumerate immediate subdirectories containing a `SKILL.md`.
- **HTTP:** cannot enumerate a static server. **Extend** the per-skill `index.json` that v0.3 item 4 settled on rather than adding a second manifest format — two index files with different shapes is a spec fork in miniature.
- Validation still runs per skill; `register_all` should report every failure rather than aborting on the first.

The required-vs-optional-method question is already answered:
[ADR 0002](../adr/0002-optional-provider-capabilities.md) established the
`supports_*` flag plus a raising default, so "cannot enumerate" is never mistaken for "found
nothing". `discover()` follows it — a `supports_discovery` flag and a
`DiscoveryNotSupportedError` default.

### Acceptance criteria

- [ ] `discover()` on the filesystem provider, following ADR 0002
- [ ] `register_all()` on the registry, atomic, reporting all validation failures at once
- [ ] Unsupported providers raise rather than returning an empty list
- [ ] HTTP behaviour consistent with the existing resource-discovery manifest
- [ ] Root README quick-start shows the shorter form

## 6. Catalog filtering and token budget

**Labels:** `theme:dx`, `theme:performance`, `type:feature`, `package:core`

### Problem

`get_skills_catalog()` returns every registered skill, and the result is injected into every
system prompt on every turn. With a large registry the catalog silently becomes a significant
fixed cost per request, and there is no way to cap or narrow it.

### Proposal

```python
await registry.get_skills_catalog(
    format="xml",
    tags=["incident"],        # filter by frontmatter metadata
    include=["skill-a"],      # explicit allow-list
    exclude=["deprecated-x"],
    max_chars=8000,           # hard ceiling
)
```

When `max_chars` would be exceeded, truncate deterministically (stable ordering, whole entries
only) and append an explicit note that the catalog was truncated — silently dropping skills
would make agent behaviour non-reproducible.

Depends on tags existing in frontmatter; decide whether to read them from the spec's `metadata`
dict or propose a dedicated field.

### Acceptance criteria

- [ ] Filtering by tags, include, and exclude
- [ ] `max_chars` enforced, truncation deterministic and flagged in the output
- [ ] Existing no-argument behaviour unchanged
- [ ] Interaction with catalog caching (v0.3 item 1 follow-ups) documented — cache key must include the filter arguments

## 7. Skill evaluation harness

**Labels:** `theme:agent-effectiveness`, `type:feature`, `package:testing`, `package:cli`

**Depends on:** item 1 (CLI), item 4 (test doubles)

### Problem

A skill is a prompt, and nobody measures whether a given skill makes an agent better. Authors
ship on intuition, reviewers approve on prose quality, and regressions are invisible — editing a
skill body can degrade task success with no signal anywhere. The whole ecosystem currently
operates on faith.

### Proposal

Test cases alongside the skill, and a runner that measures the difference the skill makes:

```yaml
# evals/deploy-rollback.yaml
skill: deploy-rollback
cases:
  - prompt: "Production is erroring after the 14:02 deploy. What do I do?"
    expect:
      - contains: "kubectl rollout undo"
      - not_contains: "kubectl delete"
      - judge: "Recommends rollback before investigating root cause"
```

`agentskills eval` runs each case twice — once with the skill registered, once without — and
reports the delta. The paired comparison is the point: absolute pass rates mostly measure the
underlying model, whereas the difference isolates the skill's contribution.

Assertions in three tiers: deterministic (`contains`, `not_contains`, `regex`), structural (a
named tool was called), and model-judged for anything subjective. Judged assertions need a
declared judge model and should report agreement, since an LLM judge is itself unreliable.

### Open questions

- Model access: BYO client via a small protocol, or depend on `litellm` for provider breadth? A protocol keeps `agentskills-testing` dependency-light.
- Non-determinism: fixed seed and temperature 0 where the provider supports it, plus `n` repeats with a pass threshold rather than a single run.
- Cost: these hit real APIs. Must be opt-in, never part of the default `pytest` run, and should cache by (skill hash, case hash, model).

### Acceptance criteria

- [ ] Eval case file format documented and validated by `agentskills validate`
- [ ] `agentskills eval` reports per-case with/without results and an aggregate delta
- [ ] Deterministic and judged assertions both supported
- [ ] Results cached by skill and case hash so unchanged cases do not re-bill
- [ ] Never runs in the default test suite; requires explicit invocation and credentials
- [ ] Example evals for the skills in `examples/skills/`

## 8. Foreign format adapters

**Labels:** `theme:interoperability`, `type:feature`, `package:adapters`

### Problem

The barrier to adopting this SDK is not the API — it is that a team has no skills written. Most
already have the content, though: `AGENTS.md`, `.github/copilot-instructions.md`, `.cursor/rules/`,
Claude skill folders, internal runbooks. Asking them to hand-convert all of it before seeing any
value is a steep first step, and an empty registry is worth nothing.

### Proposal

A new `agentskills-adapters` package converting foreign formats into `Skill` objects at load
time:

| Source | Mapping |
|---|---|
| `AGENTS.md` / `copilot-instructions.md` | Whole file becomes one skill body; name and description derived from the first heading, or synthesised |
| `.cursor/rules/*.mdc` | One skill per rule file; `description` and `globs` frontmatter map across directly |
| Claude skill folders | Near-identical structure; largely a validation pass |

This is an **import layer, not a spec fork** — principle 1 holds because nothing new is added to
the skill format. Adapters produce ordinary `Skill` objects that the registry cannot distinguish
from native ones.

The honest limitation: formats without a description field lose the catalog entry that
progressive disclosure depends on, since the agent selects on description. Options are to
synthesise one, or require the user to supply it. `agentskills init --from <path>` should emit a
real `SKILL.md` for editing, so adapters are a migration on-ramp rather than a permanent
dependency.

### Acceptance criteria

- [ ] Adapters for `AGENTS.md`, Copilot instructions, and Cursor rules
- [ ] Output passes `validate_skill()` and the provider conformance suite
- [ ] Missing descriptions handled explicitly, never silently blank
- [ ] `agentskills init --from <path>` converts to a native `SKILL.md`
- [ ] Documented as a migration path, with its limitations stated

## 9. Token cost reporting

**Labels:** `theme:dx`, `type:feature`, `package:cli`, `good-first-issue`

> **Partly answered by item 1.** `inspect` already reports the catalog entry and body with an
> estimate, and `lint` enforces a body budget — but both count `len(text) / 4`. What is left
> here is the per-section breakdown and a real tokenizer, which means deciding whether the CLI
> takes a `tiktoken` dependency or ships the estimate with the caveat attached.

### Problem

Skill authors have no visibility into what their skill costs. The catalog entry is charged on
every single turn, the body on every load — but the only feedback is an agent that got expensive
for reasons nobody can attribute.

### Proposal

`agentskills inspect --cost` breaking the skill into what is actually charged and when:

```
deploy-rollback
  catalog entry        142 tokens   (every turn)
  body               3,180 tokens   (on load)
    ## Overview        410
    ## Procedure     2,240
    ## References      530
  references/api.md  1,890 tokens   (on demand)
```

Separating per-turn from per-load cost is the part that matters — a bloated description is far
more expensive than a bloated body, and that is exactly backwards from most authors' intuition.

Use `tiktoken` if available, fall back to a character heuristic with the estimate flagged as
approximate. Add `--budget` to exit non-zero above a threshold so CI can gate it.

### Acceptance criteria

- [ ] Per-turn and per-load costs reported separately
- [ ] Body broken down by section
- [ ] Works without `tiktoken`, marking output as estimated
- [ ] `--budget` exits non-zero when exceeded
- [ ] `--format json` for CI consumption

## 11. Architecture decision records

**Labels:** `theme:project-health`, `type:docs`

**Status:** Started — [`docs/adr/`](../adr/) has ADR 0001 and 0002.

### Problem

Cross-package decisions are undocumented, so they get re-litigated or silently reversed. Git
history shows what changed, not which alternatives were rejected and why.

### Proposal

Backfill ADRs for decisions already made:

| Decision | Why it needs a record |
|---|---|
| Fully async provider interface | Constrains every provider implementation; the fs provider was sync-under-async until v0.3 item 3 |
| Six packages instead of one with extras | Shapes install UX, release process, and version coordination — and the lockstep versioning rule the release guard now enforces |
| Caching strategy | Why provider caching is per-instance with an explicit `invalidate()`, and why HTTP revalidation is opt-in rather than default |
| Exception taxonomy | Extended by v0.3 item 7 with `SkillUnavailableError`; the rationale for splitting "not found" from "unavailable" exists only in issue notes |
| Binary resources as a JSON envelope | Chosen for consistency across integrations over MCP-native content blocks. Write this before the follow-up that reverses it |
| Logging conventions | Why one `agentskills.*` namespace, and why there is deliberately no `ERROR` level |

Add a short `docs/adr/README.md` with the template and the numbering convention.

### Acceptance criteria

- [ ] ADR template and index in place
- [ ] Backfill ADRs written for the decisions above
- [ ] Each links to the issue or PR where the decision was made
- [ ] Contributing guide points at ADRs for design-affecting changes

## 12. Simplify the publish workflow: drop the TestPyPI path

**Labels:** `theme:project-health`, `type:chore`

> **Status: implemented.** The fall-through became an explicit refusal, `workflow_dispatch` now
> stops at the artifact, and pre-releases go to PyPI; see the implementation notes.

### Problem

The publish workflow routes any tag that is not a bare `vX.Y.Z` to TestPyPI as a dry run. That
path is configured for exactly one of the seven packages, and finishing it is more work than it
looks: **pending trusted publishers must be uniquely identifiable by their claims.** All seven
distributions share the same owner, repository, workflow and environment, so PyPI cannot tell
which pending project an incoming token belongs to and permits only one pending publisher at a
time. Bootstrapping the set on a fresh index therefore takes as many sequential publish rounds
as there are packages, each one converting a pending publisher into a project-scoped one and
freeing the slot.

So today an `rc` tag publishes `agentskills-core` and then fails. That is worse than having no
dry run, because it fails in a way that looks like a real problem.

The routing has a second weakness that only shows up once TestPyPI is gone. A malformed tag does
not *fail* — it falls through to the other index. The safety property was never "unexpected tags
are rejected", it was "unexpected tags land somewhere else", and that is only safe while
somewhere else exists.

### Proposal

- Replace the fall-through with an explicit refusal: a tag that does not match the version
  pattern fails the run with a message naming the expected shape.
- Make `workflow_dispatch` a build-only dry run — run the version guard, build all six, upload
  the artifact, publish nothing.
- Let pre-release tags publish to PyPI, which handles them natively; `pip` will not install a
  pre-release unless `--pre` is passed, so TestPyPI was never required for this.
- Delete the `testpypi` environment and its trusted publisher.

### Acceptance criteria

- [x] A tag of an unexpected shape fails loudly instead of publishing anywhere
- [x] `workflow_dispatch` validates and builds without uploading
- [x] Pre-release tags publish to PyPI
- [x] `DEVELOPMENT.md` documents the pending-publisher uniqueness limit

### Observations to carry in

The 0.3.0 release proved the OIDC exchange, the claim set, the build loop and the version guard
end-to-end against production PyPI — which is what the TestPyPI rehearsal existed to prove.
What would remain untested without it needs no index at all.

The pending-publisher limit should be documented **regardless of the outcome of this issue**,
because it applies to any new index and to adding a seventh package.

### Implementation notes

**The tag pattern is an allow-list of two shapes, not a rejection of one.** `vX.Y.Z` releases,
`vX.Y.Z` plus `a1`/`b1`/`rc1` pre-releases, and everything else fails with a message naming what
was expected. The previous routing was also an allow-list, but its `else` branch was another
index; once that index is gone the same structure fails *open*, and the fix is a branch that
exits non-zero rather than a different destination.

**Pre-release is now a property of the tag rather than of the destination.** The GitHub Release's
`prerelease` flag used to be derived from `environment == 'testpypi'`, which coupled a
release-notes detail to a publishing target that no longer exists. The `guard` job emits it
directly.

**`workflow_dispatch` stops after the artifact.** It still runs the version guard and builds all
seven distributions, which is what a dry run was ever able to catch here. What it cannot exercise
is the upload — and that was true of the TestPyPI path too, because it only ever uploaded one
package before failing.

**`repository-url` is gone from all seven publish steps rather than hardcoded to PyPI.** The
action defaults there. A URL repeated seven times is seven places to be wrong about the same
fact.

### Observations for later

**`scripts/publish.{ps1,sh}` still offer `--test-pypi`.** They are the token-based emergency
path for releasing when Actions is down, and a scratch index is genuinely useful when you are
already off the rails. Left alone deliberately: nothing about them depends on the trusted
publisher this issue removes.

**Nothing now exercises an upload before a real one.** That is the honest cost of this change and
it was already the situation, since the dry run could only ever publish one package out of seven.
The mitigation is `skip-existing`, which makes a failed release re-runnable rather than
unrepeatable.
