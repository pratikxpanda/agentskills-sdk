## Release Goal

Prepare the maintained eleven-package SDK for explicit compatibility commitments. Complete
config-driven publication across existing providers, consolidate console ownership, and establish
evidence for the API, client, deployment, and release contracts that v1.0 will freeze.

Version 0.9.0 has been published. Publication does not by itself close the external validation
criteria below; record their evidence or an explicit deferral before treating them as complete.
No v1.0 compatibility guarantee is implied.

## 1. Unified Serving CLI

Status: implemented and published in v0.9.0.

Only `agentskills-tools` installs the `agentskills` console command. The MCP distribution removes
`agentskills-mcp` without a console alias and retains `python -m agentskills_mcp_extension`.
This is a breaking change and must appear prominently in the release notes.

Acceptance criteria:

- `agentskills serve PATH` retains existing folder behavior.
- `agentskills serve --config FILE` uses the integration's JSON/YAML configuration loader,
  publication policy, snapshot capture, and owned-provider cleanup.
- Folder and config input are mutually exclusive. Config mode rejects folder-only flags instead
  of silently overriding configured name, limits, or prompt settings.
- `--check` never starts a listener. Config mode retains the integration's JSON readiness report.
- Installing all distributions into a clean environment creates one console owner and no
  `agentskills-mcp` launcher. Both console and module preflight are exercised.
- Migration guidance covers installation, command arguments, and MCP host subprocess settings.

## 2. Existing Providers in Server Configuration

Status: implemented and published in v0.9.0.

The resolver supports `fs`, `http`, `git`, `azure-blob`, `azure-files`, and `oci`. These are existing
provider implementations, not new distributions or alternate publication formats.

Acceptance criteria:

- Provider imports remain lazy. A missing optional SDK does not prevent filesystem publication.
- Missing-package errors identify the provider distribution and its service extra when relevant.
- New provider options are typed, reject unknown keys, and cannot inject runtime clients or
  credentials through JSON. Error output does not echo rejected secret values.
- Git configuration preserves ref resolution, cache bounds, and subdirectory behavior. A real
  local-repository preflight succeeds without external network access.
- Azure Blob and Azure Files keep independent dependency extras. FileREST backup intent remains
  explicit and documented with its RBAC and ACL implications.
- OCI keeps TLS enabled by default and uses the existing ORAS authentication and artifact contract.
- Configuration delegates file access and limits to providers and snapshots. It does not execute
  scripts or bypass trust policy. Owned clients close after capture and on failure.
- Tests distinguish constructor forwarding and controlled-source publication from production
  Azure permissions or registry compatibility certification.

## 3. Public API Audit

Status: inventory and findings are recorded in the compatibility guide; the v1.0 API freeze
remains an open decision.

The [API inventory](../compatibility.md) records package roots, documented submodules, provider
and test-fixture contracts, CLI/data boundaries, and decisions required before stability.
Installed-wheel verification checks declared root exports resolve without duplicates. It does
not freeze signatures or approve removing a documented API. Remaining boundary and version-range
decisions are listed explicitly rather than treated as completed work.

Inventory public imports, callable signatures, provider capabilities, exception types, CLI flags,
JSON output schemas, and documented configuration across all eleven packages.

Acceptance criteria:

- Each package has an explicit supported surface and identified private implementation details.
- The audit compares documented entry points with exports and actual callers, including lazy and
  framework-neutral integration paths.
- Necessary breaking changes are listed individually with rationale, migration guidance, and
  regression checks. An audit does not authorize unrelated cleanup or broad refactoring.
- Maintainer decisions resolve ambiguous APIs before any v1.0 freeze is claimed.

## 4. Compatibility Policy

Status: the pre-1.0 policy was approved and published in v0.9.0; stable-release commitments remain
open for v1.0.

The maintainer approved same-minor sibling dependency ranges during 0.x and at least one released
minor of deprecation before future removals. The policy, transition exception for the v0.9 console
removal, and current supported-version evidence are recorded in the
[compatibility guide](../compatibility.md) and [ADR 0012](../adr/0012-pre-1-compatibility.md).
Both bump scripts and the release checker have disposable-fixture regression tests in CI.

Define the guarantees that users can rely on across packages, Python runtimes, MCP versions,
configuration, and output schemas.

Acceptance criteria:

- Specify supported Python and MCP SDK/protocol ranges from tested evidence.
- Document lockstep package compatibility and the treatment of optional provider installations.
- Agree a deprecation window and removal process, including warnings and release-note requirements.
- Separate pre-1.0 policy from future stable-API commitments. Do not promise support for retired
  framework integrations or external hosts that have not been tested.

## 5. Authenticated Deployment Validation

Status: local authorization checks are implemented; external deployment validation remains open.

Local ASGI tests cover accepted initialization and rejection of missing, invalid, expired,
wrong-audience, and insufficient-scope credentials, plus host/origin restrictions. They use a
controlled verifier and do not supply a TLS endpoint or certify a production identity provider.

Close the deployment-validation gap explicitly deferred since v0.6. Local constructor and loopback
tests are not evidence of production TLS or identity configuration.

Acceptance criteria:

- Exercise a TLS-fronted Streamable HTTP deployment with deployment-owned MCP authorization.
- Verify valid access and rejection of missing, invalid, expired, and wrong-audience credentials.
- Exercise configured host/origin restrictions and isolation between server audiences.
- Confirm inbound bearer tokens are not passed upstream to skill providers.
- Record the tested environment and responsibility boundaries. Provisioning, identity changes,
  and billable infrastructure require separate authorization.

## 6. Host Interoperability

Status: local SDK client checks and a reproducible example are implemented; external host claims
remain excluded without validation.

The documentation checker executes the official SDK client example over stdio. The clean-wheel
job runs native client/server regressions against installed artifacts and the resolved supported
MCP SDK. The dedicated floor job retains pinned mcpc 0.7.0 validation. The
[client support matrix](https://github.com/pratikxpanda/agentskills-sdk/blob/main/packages/integrations/agentskills-mcp-extension/README.md#client-support-and-boundaries)
separates these checks from host activation and production deployment certification.

Acceptance criteria:

- Publish reproducible MCP client examples with pinned, tested client versions.
- Distinguish ordinary tools/resources connectivity from native Skills extension negotiation.
- Verify metadata-only discovery, direct lookup, exact resource bytes, digest checking, pagination,
  and origin preservation against the supported client matrix.
- Identify selection, consent, context injection, and execution as host responsibilities.
- Document unsupported capabilities as gaps rather than adding retired lifecycle adapters.

## 7. Release Verification

Status: v0.9.0 was published; post-publication fresh-install checks remain open.

All eleven packages are prepared at 0.9.0 with same-minor sibling ranges. External lock records
are preserved. Version-policy regressions, installed export checks, client round trips, executable
docs, and the pre-tag checklist are part of the validation path. This is not a published release.

Acceptance criteria:

- Retain clean wheel/sdist checks, Linux/Windows installed-command smoke jobs, version alignment,
  lock consistency, declared-dependency checks, executable docs, and package coverage floors.
- Verify fresh PyPI installations of the supported provider/service extras after publication.
- Document sequential pending Trusted Publisher bootstrapping with safe failed-job retries.
- Make breaking-change review a release gate before tagging. Preserve generated release links
  when adding migration notices.
- Keep immutable published artifacts and approved environment gates. Never move a release tag to
  patch a partially published version.

## Out of Scope

- New providers without demonstrated demand
- Native framework lifecycle adapters
- Server-side federation or rehosting remote skills
- Script execution, a hosting UI, or an SDK-owned identity service
- Automatic activation, approval, or tool permission grants

## Completion

v0.9.0 has been published. Remaining external validation criteria are complete only when their
evidence is recorded or the maintainer explicitly revises the scope. API freeze and stable-API
guarantees remain v1.0 decisions.
