## Release Goal

Establish the first stable compatibility contract for the maintained SDK packages and publish
1.0.0 only after the supported API, compatibility policy, release process, and MCP interoperability
boundaries have maintainer approval and verifiable evidence.

This specification is a proposal. It does not itself freeze APIs, promise compatibility, or close
any open v0.9 acceptance criteria. The v0.9 record identifies external deployment, host
interoperability, and post-publication installation checks that need an explicit disposition before
they are treated as complete.

## 1. Stable API

Define the supported public API for each maintained package, using the [compatibility inventory](../compatibility.md)
as a starting point.

Acceptance criteria:

* The maintainer approves which package roots, submodules, provider contracts, fixtures, CLI
  commands, configuration keys, exceptions, and serialized output schemas are stable.
* Public documentation matches the approved API and identifies unsupported or private interfaces.
* Every incompatible change needed before the freeze has an explicit rationale, migration guidance,
  and regression coverage. No unrelated cleanup is bundled into the freeze.
* Installed-artifact checks verify the approved public surface and documented entry points.

## 2. Stable Compatibility Policy

Replace the pre-1.0 policy with explicit stable-release guarantees based on tested support evidence.

Acceptance criteria:

* The maintainer approves supported Python versions, MCP SDK and protocol revisions, and the
  compatibility guarantees between the independently installable packages.
* Optional provider and integration extras have documented installation and compatibility
  boundaries; core remains usable without optional dependencies.
* The maintainer approves SemVer rules for additions, deprecations, removals, behavioral changes,
  configuration, and output schemas.
* The deprecation and removal process states the minimum notice period, warning behavior, migration
  documentation, and release-note requirements.
* Compatibility statements distinguish verified support from permitted-but-untested combinations.

## 3. Reproducible Release Process

Make the 1.0.0 release reproducible across all maintained distributions and preserve the existing
publishing safeguards.

Acceptance criteria:

* All packages have aligned 1.0.0 metadata and compatible sibling constraints; lockfiles and
  release checks agree with the published package inventory.
* CI verifies clean wheels and source distributions, installed commands on supported operating
  systems, declared dependencies, executable documentation, and package coverage floors.
* Trusted Publishing, attestations, protected-environment approvals, and safe retry behavior are
  exercised and documented.
* Changelog and release-note generation includes migration guidance and correctly categorized
  changes.
* Fresh installation checks cover the supported packages and optional provider extras after
  publication. Published artifacts remain immutable; a failed release is corrected with a new
  version.

## 4. MCP Interoperability Contract

Stabilize the SDK's MCP-facing contracts without claiming that the SDK owns host lifecycle,
selection, approval, or execution behavior.

Acceptance criteria:

* Protocol conformance verifies discovery, direct lookup, resource reads, content integrity,
  pagination, and origin-preserving composition against the supported client matrix.
* The supported MCP SDK and protocol revisions are recorded with reproducible test evidence.
* Authorization ownership, audience isolation, origin boundaries, and inbound credential handling
  are documented and tested at the SDK boundary.
* Host-specific claims are limited to tested versions and capabilities. Unsupported host behavior
  is documented as a gap, not implied by basic MCP connectivity.
* Telemetry and integrity metadata contracts are documented, tested, and do not disclose skill
  content or credentials.

## Open Decisions

Resolve these with the maintainer before declaring the API frozen or tagging 1.0.0:

* Confirm that all eleven maintained packages are in the initial stable contract.
* Approve the exact stable API surface and any required pre-freeze breaking changes.
* Set tested support ranges and compatibility guarantees for Python, MCP, and sibling packages.
* Approve stable SemVer, deprecation, and removal commitments.
* Decide whether the open v0.9 external validation gates block 1.0.0 or remain explicitly deferred,
  with separate evidence and authorization where needed.
* Confirm the host/client matrix and which deployment configurations can be validated for the
  release.

## Out of Scope

* New providers or native framework lifecycle adapters without separately approved scope
* Server-side federation, script execution, a hosting UI, or an SDK-owned identity service
* Compatibility claims for untested hosts, interpreters, or optional dependency combinations

## Completion

v1.0 is ready when the maintainer-approved stable contract is documented, all required release
gates pass against clean installed artifacts, open v0.9 gates have an explicit disposition, and
the 1.0.0 artifacts are verified after publication.
