## 1. Cache `SKILL.md` content in providers

**Labels:** `theme:performance`, `type:feature`, `package:fs`, `package:http`

### Problem

`LocalFileSystemSkillProvider` and `HTTPStaticFileSkillProvider` re-fetch and re-parse
`SKILL.md` on **every** call to `get_metadata()` or `get_body()`. A single skill is read up
to five times in one agent session:

| # | Code path | Trigger |
|---|---|---|
| 1 | `validate_skill()` → `skill.get_body()` | Registration |
| 2 | `validate_skill()` → `skill.get_metadata()` | Registration |
| 3 | `registry.get_skills_catalog()` → `skill.get_metadata()` | System prompt / MCP resource read |
| 4 | tool call → `skill.get_metadata()` | Agent turn |
| 5 | tool call → `skill.get_body()` | Agent turn |

For the HTTP provider that is five network round-trips for one file. For the filesystem
provider the I/O is cheaper but the redundant YAML parsing remains.

### Proposal

Add a content cache keyed by `skill_id` to the internal `_get_skill_md()` / `_read_skill_md()`
helper in both providers.

```python
self._skill_md_cache: dict[str, str] = {}

async def _get_skill_md(self, skill_id: str) -> str:
    if skill_id not in self._skill_md_cache:
        self._skill_md_cache[skill_id] = await self._fetch(...)
    return self._skill_md_cache[skill_id]
```

Cache is per provider instance. No public API change.

For HTTP, prefer **conditional requests** (`If-None-Match` / `If-Modified-Since` using the
stored `ETag` / `Last-Modified`) over a blind TTL — a `304` costs one cheap round-trip and
keeps long-lived servers correct when a skill is republished. Expose an explicit
`invalidate(skill_id=None)` for callers that need it.

### Acceptance criteria

- [x] HTTP provider issues exactly one request per skill across a full register → catalog → tool-call flow (assert on mocked `httpx` call count)
- [x] Filesystem provider reads each `SKILL.md` once (spy on `Path.read_text`)
- [x] Cache is per-instance — two providers do not share state
- [x] `invalidate()` clears one skill or all
- [x] HTTP revalidates with `ETag`/`Last-Modified` and handles `304`
- [x] Existing tests pass unchanged

### Implementation notes

**Status: implemented, awaiting release.**

Two acceptance criteria conflict: "exactly one request per skill" and "revalidates with
`ETag`/`Last-Modified`" cannot both hold under one default, because revalidation costs a
round-trip per access even when it returns `304`. Resolved by making revalidation opt-in:
`HTTPStaticFileSkillProvider(..., revalidate=True)`. The default serves cached content until
`invalidate()` is called, which is right for the common case (a static host, a process that
outlives a few agent turns). Long-lived servers fronting a mutable host should opt in.

Only `SKILL.md` is cached. Scripts, assets and references are left uncached: they are larger,
typically read once, and caching them would make the provider's memory footprint depend on
untrusted content size.

### Related follow-ups (file separately if wanted)

- `validate_skill()` calls `get_body()` and `get_metadata()` independently, parsing twice. Fetch and split once.
- `SkillRegistry.get_skills_catalog()` re-derives metadata for every skill on each call; the registry has no `unregister()`, so the catalog string can be memoised.
- Both providers duplicate `_get_skill_md()` → `split_frontmatter()`; a shared helper returning `tuple[dict, str]` avoids double parsing.

## 2. Build the skills catalog concurrently

**Labels:** `theme:performance`, `type:feature`, `package:core`

### Problem

`SkillRegistry.get_skills_catalog()` awaits `get_metadata()` for each skill in sequence. With
an HTTP-backed registry of N skills that is N serial round-trips on the critical path of the
first agent turn.

### Proposal

Fan out with `asyncio.gather` and a bounded semaphore (default concurrency ~8, configurable).
Preserve deterministic ordering by sorting results after the gather, not relying on completion
order.

### Acceptance criteria

- [x] Catalog output is byte-identical to the serial implementation for the same registry
- [x] Metadata fetches run concurrently (assert with an instrumented provider)
- [x] Concurrency is bounded and configurable
- [x] A failure in one skill's metadata surfaces with the offending `skill_id` in the message

### Implementation notes

**Status: implemented, awaiting release.**

Concurrency is bounded by an `asyncio.Semaphore` and configured per registry:
`SkillRegistry(catalog_concurrency=8)`. Values below 1 raise `ValueError`.

Ordering is preserved by zipping the `asyncio.gather` results back against `list_skills()`
rather than sorting afterwards — `gather` already returns results in argument order, so no
sort is needed and the catalog stays byte-identical to the serial version.

Skill ID context is attached with `exc.add_note()` (PEP 678) rather than by wrapping in a new
exception. Wrapping would have changed the exception *type* callers see, breaking anyone
catching `SkillNotFoundError` from a catalog build.

## 3. Stop blocking the event loop in the filesystem provider

**Labels:** `theme:performance`, `type:bug`, `package:fs`

### Problem

`LocalFileSystemSkillProvider` exposes an `async` interface but reads synchronously via
`Path.read_text()` / `read_bytes()`. Every skill read blocks the event loop, which matters for
servers handling concurrent agent sessions (including the MCP server in streamable-HTTP mode).

### Proposal

Move blocking I/O to a worker thread (`asyncio.to_thread`, or `anyio.to_thread.run_sync` to
stay loop-agnostic). Keep the size check before the read where possible so oversized files are
rejected without loading them.

### Acceptance criteria

- [x] No blocking filesystem calls on the event loop
- [x] Size limit still enforced
- [x] Concurrent reads from one provider work correctly

### Implementation notes

**Status: implemented, awaiting release.**

Used `asyncio.to_thread` rather than `anyio.to_thread.run_sync`. Loop-agnosticism was not
worth a new runtime dependency on a provider package whose only current dependency is
`agentskills-core`; the rest of the SDK is asyncio-based already. Revisit if anyone asks for
Trio support.

The *whole* helper moved to the worker thread, not just the `read_text()` call. The
path-traversal guard (`Path.resolve()`, `is_dir()`, `is_file()`, `stat()`) issues syscalls
too, and on a cold cache or a network mount those dominate. Moving only the read would have
left most of the blocking behind.

## 4. Add resource discovery to the provider contract

**Labels:** `theme:correctness`, `type:feature`, `package:core`, `package:fs`, `package:http`

> **Status: implemented.** The `breaking-change` label was dropped — the chosen design adds
> no abstract method, so existing third-party providers keep working unchanged.

### Problem

There is no way for an agent to learn which references, scripts, or assets a skill contains.
`get_reference(skill_id, name)` requires a name the agent can only obtain if `SKILL.md` happens
to mention it in prose. Progressive disclosure is effectively half-blind: the agent can fetch
a resource but cannot enumerate one.

### Proposal

Add to `SkillProvider`:

```python
async def list_resources(self, skill_id: str) -> dict[str, list[str]]:
    """Return available resource names grouped by kind: references, scripts, assets."""
```

- **Filesystem:** list the `references/`, `scripts/`, `assets/` subdirectories, applying the same identifier-safety rules used on read.
- **HTTP:** static servers cannot be enumerated. Suggest an optional per-skill `index.json` manifest — which also gives the supply-chain work a natural home for integrity hashes.
- Surface as a `list_skill_resources` tool in each integration and as an MCP resource.

### Open question

Adding a required abstract method is a **breaking change** for any third-party `SkillProvider`.
Options:

1. Required abstract method — clean contract, breaks implementors.
2. Default implementation returning `{}` plus a `supports_resource_listing` capability flag — backward-compatible, weaker contract.

Recommend (2) pre-1.0, revisiting at the API freeze.

### Acceptance criteria

- [x] Decision recorded as an ADR before implementation
- [x] `list_resources()` on the provider contract
- [x] Filesystem implementation, with traversal guards
- [x] HTTP behaviour decided and implemented
- [x] Exposed through LangChain, Agent Framework, and MCP integrations
- [x] Documented in each package README

### Implementation notes

**Deviation from option 2: the default raises, it does not return `{}`.**
A default returning `{}` makes "I cannot enumerate this skill" indistinguishable from "this
skill has no resources". That is the same failure class as the binary-corruption bug in item 5
— a silently wrong answer is worse than a loud one, because nothing downstream can detect it.
The default now raises `ResourceListingNotSupportedError`, which subclasses both
`AgentSkillsError` and `NotImplementedError` so callers can catch it from either hierarchy.
The capability flag from option 2 is kept, so callers can branch *before* paying for a call.
Recorded in ADR 0002 along with the alternatives rejected (mixin ABCs cannot express a
per-instance capability, which the HTTP provider needs).

**The flag is a plain class attribute, not a `ClassVar`.** The HTTP provider's capability
depends on its constructor argument, not on its type.

**Filesystem: skip, do not raise.** Dotfiles, subdirectories, and symlinks resolving outside
the root are silently omitted. Raising would let one stray `.DS_Store` or editor swapfile make
a whole skill unlistable. The stricter invariant that matters is the inverse one: listing must
never return a name that a subsequent `get_reference()` would reject.

**HTTP: manifest is opt-in, and a missing manifest is also "not supported".** `index.json` is
read only when the provider is constructed with `resource_manifest=True`. If that is set but a
given skill has no manifest, the 404 is translated to `ResourceListingNotSupportedError` rather
than an empty listing — same reasoning as above. Manifest entries are host-supplied data that
get interpolated into URLs, so names failing the existing identifier check are dropped rather
than trusted.

**Integrations return, not raise, on unsupported.** The `list_skill_resources` tool catches
`ResourceListingNotSupportedError` and returns `{"supported": false, "note": "..."}`. For an
LLM caller, "this cannot be listed" is actionable information (fall back to the skill body),
whereas a tool error invites a retry loop. The MCP server exposes the same data as a resource
template, `skills://{skill_id}/resources`.

**Observation for v0.4.** Three of the six tools in every integration are now near-identical
`skill_id`/`name` wrappers over `encode_resource_content()`. The tool layer is ready to be
generated from a single table rather than hand-written per framework.

## 5. Stop corrupting binary skill resources

**Labels:** `theme:correctness`, `type:bug`, `package:core`, `package:langchain`, `package:agentframework`, `package:mcp-server`

### Problem

All three integrations decode provider bytes the same way:

```python
return (await skill.get_asset(name)).decode("utf-8", errors="replace")
```

For any non-text resource — a PNG, a PDF, a zip — `errors="replace"` turns the payload into a
run of U+FFFD replacement characters. The data is destroyed, no exception is raised, and the
agent receives garbage it cannot distinguish from a legitimately odd document. The package
READMEs currently document this as a "Note", which presents silent data loss as intended
behaviour.

The skill spec allows `assets/` to hold arbitrary files, so this is reachable through the
documented happy path rather than an edge case.

### Proposal

A shared `encode_resource_content()` in `agentskills-core`, used by all three integrations so
the behaviour cannot drift apart again:

1. Sniff for binary content (null byte within the first 8 KiB).
2. If it looks like text, attempt a **strict** UTF-8 decode and return the string on success.
3. Otherwise return a JSON envelope carrying the media type (via `mimetypes`) and base64 content:

```json
{
  "name": "architecture.png",
  "media_type": "image/png",
  "size_bytes": 20481,
  "encoding": "base64",
  "content": "iVBORw0KGgo..."
}
```

Base64 costs roughly 1.37x the raw bytes in characters, and a 1 MiB image would swamp a context
window. Above a `max_inline_binary_bytes` ceiling (default 64 KiB, caller-overridable) return
the same envelope with `"encoding": "none"` and a `note` explaining the omission, so the agent
learns the resource exists and why it was not inlined.

The strict decode in step 2 matters: it is what converts a silent corruption into a detected
one. Falling back to the envelope on `UnicodeDecodeError` means no input path can produce
replacement characters.

### Open question

MCP supports typed binary content blocks and resource links natively, so the JSON envelope is a
lowest-common-denominator choice there. Options: ship the envelope everywhere first for
consistency and specialise the MCP server afterwards, or diverge immediately. The envelope is
the smaller change and keeps one code path; the MCP specialisation is worth doing but is a
separate piece of work.

### Acceptance criteria

- [x] No integration calls `.decode("utf-8", errors="replace")` on resource bytes
- [x] A PNG asset round-trips: `base64.b64decode(envelope["content"]) == original_bytes`
- [x] `media_type` inferred from the resource name
- [x] UTF-8 text resources unchanged, including non-ASCII
- [x] Text that is valid UTF-8 but contains a null byte still returns intact
- [x] Oversized binaries return `"encoding": "none"` with an explanatory note, not truncated content
- [x] `max_inline_binary_bytes` overridable on `get_tools()` and `create_mcp_server()`
- [x] READMEs describe the envelope; the existing "replacement characters" note is removed

### Implementation notes

**Status: implemented, awaiting release.**

The null-byte sniff in step 1 of the proposal was dropped. It contradicts the fifth acceptance
criterion — valid UTF-8 containing a null byte would have been classified binary and wrapped in
an envelope. The implementation is decode-first: attempt a strict UTF-8 decode, fall back to the
envelope on `UnicodeDecodeError`. That is also cheaper than it looks, because a strict decode
fails at the *first* invalid byte rather than scanning the whole payload. One code path, and no
input can produce a replacement character.

The ceiling comparison is `len(data) > max_inline_binary_bytes`, so a resource exactly at the
limit is still inlined. `max_inline_binary_bytes=0` never inlines; negative values raise
`ValueError`.

Two existing tests asserted the corruption was intended —
`test_binary_content_decoded_with_replacement` in the LangChain and Agent Framework suites
asserted `"\ufffd" in result`. Both were replaced with round-trip assertions. Worth noting as a
pattern: the bug was covered by tests, documented in three READMEs, and still a bug.

### Follow-up

Once the envelope lands, have `create_mcp_server()` return binary resources as native MCP
binary content blocks — or a resource link when oversized — rather than a JSON string the client
has to parse. Text behaviour unchanged, and `encode_resource_content()` stays as-is for the
non-MCP integrations.

## 6. Optional `version` field in skill frontmatter

**Labels:** `theme:correctness`, `type:feature`, `package:core`

### Problem

Skills have no version. Consumers cannot pin, compare, or detect drift, and
[Agent Skills Hub](https://github.com/pratikxpanda/agentskills-hub) needs versioned publishing
and subscription pinning.

### Proposal

Optional `version` frontmatter field, validated as semver **when present**, surfaced through
`get_metadata()` and included in the catalog. Fully backward-compatible — absence is valid.

Raise the field with the upstream spec rather than shipping a silent proprietary extension.

### Acceptance criteria

- [ ] `version` validated as semver when present, ignored when absent
- [ ] Returned by `get_metadata()`
- [ ] Invalid semver fails registration with a clear message
- [ ] Documented as an optional, non-spec field pending upstream adoption

### Pre-implementation notes

**The criteria contradict each other.** "Fully backward-compatible" and "invalid semver fails
registration" cannot both hold: any skill already carrying a non-semver `version` field
registers today and will stop registering. That is the right trade-off, but it is a breaking
change for those skills and should be stated as one rather than described as compatible.

**YAML coerces the field before we ever see it.** `version: 1.0` parses as a `float`,
`version: 1` as an `int`, and `version: 2024-01-15` as a `datetime.date`. A validator that
assumes `str` will raise an opaque `TypeError` on the three most likely authoring mistakes.
Non-`str` values need an explicit error telling the author to quote the value.

**No new dependency.** `agentskills-core` depends only on `pyyaml`; use the official semver
regex from semver.org rather than pulling in a package for one match.

## 7. Distinguish "not found" from "unavailable" in the HTTP provider

**Labels:** `theme:resilience`, `type:bug`, `theme:security`, `package:core`, `package:http`

> **Status: implemented.** Scope grew to include `agentskills-core` (the new
> `SkillUnavailableError`) and a credential leak confirmed during the work.

### Problem

`HTTPStaticFileSkillProvider` maps every non-2xx response — and every transport failure — to
`SkillNotFoundError`. A `503`, a DNS failure, and a genuine `404` are indistinguishable to the
caller, so nobody can implement sensible retry or alerting. A transient blip currently looks
like a missing skill.

### Proposal

- New `SkillUnavailableError(AgentSkillsError)` in core for transient/transport failures.
- `404`/`410` → `SkillNotFoundError`. `5xx`, `429`, timeouts, connection errors → `SkillUnavailableError`.
- `401`/`403` get a distinct message that does not echo credentials.
- Bounded retry with exponential backoff and jitter for retryable classes only; honour `Retry-After`. Retry count and timeout configurable on the constructor.

### Acceptance criteria

- [x] Error taxonomy implemented and documented in the package README error table
- [x] Retries only on retryable classes, with a cap
- [x] `Retry-After` honoured
- [x] No credential material in any exception message
- [x] Tests per status class via `respx`

### Pre-implementation notes

**The "no credential material" criterion is already violated today, via exception chaining.**
The provider raises `AgentSkillsError(...) from exc`, and the chained `httpx` exception's repr
contains the full request URL — including the query string. Any deployment passing a SAS token
or signed-URL credential through `params` leaks it into every traceback and every log line that
renders one. Sanitising only the message we construct is not sufficient; the cause has to be
suppressed or the URL redacted before chaining. This is a live issue, not a future one, and it
is the reason this item should be treated as security-relevant rather than purely ergonomic.

**Retry must not swallow 304.** `_stream_bytes` returns `(None, headers)` on a conditional-request
hit. A retry wrapper that treats "no body" as a failure would break revalidation, and 304 must
not be classified as unavailable.

**Retries interact with the manifest path.** A missing `index.json` is an expected 404 that is
translated to `ResourceListingNotSupportedError`; it must stay on the non-retryable branch.

### Implementation notes

**The credential leak was real and is fixed.** Confirmed: `raise_for_status()` produces an
`httpx.HTTPStatusError` whose message embeds the full URL, query string included, and chaining
it put that into every rendered traceback. The cause is now suppressed with `from None`
throughout the request path. Two regression tests assert on
`traceback.format_exception(...)` output rather than on `str(exc)` — testing only the message
would not have caught the original bug, since the message was already clean.

**Messages carry a base-relative path, not a redacted absolute URL.** The first attempt
redacted the query string and kept scheme and host, which is the conventional fix. It was
abandoned because an existing security test asserts the base URL never appears in a message at
all, and that guarantee is worth keeping: the host is the one piece an operator can always
recover from configuration, whereas a leaked path in a shared log is not recoverable. Errors
now read `HTTP 503 from /incident-response/SKILL.md`, which is enough to debug.

**`401`/`403` are `AgentSkillsError`, not `SkillUnavailableError`.** Retrying a rejected
credential is pointless and, against hosts with lockout policies, harmful. They get a message
naming `headers`/`params` as the thing to check, without echoing either.

**A `Retry-After` beyond `max_retry_delay` fails immediately rather than sleeping.** Honouring
a literal `Retry-After: 3600` would park a request path for an hour. The advice is not
discarded — it is attached to the exception as `retry_after` so a scheduler can act on it — but
the decision to wait that long belongs to the caller, not to a provider.

**Full jitter, not equal jitter.** `random.uniform(0, delay)`. The registry builds its catalog
concurrently, so without jitter every skill fetch retries in lockstep and hits the recovering
server as a single wave. The tests pin the *bound* by stubbing `random.uniform`, not the value.

**304 stayed on the success path**, as flagged above; the revalidation tests already covered it
and continue to pass unchanged.

**Observation.** `SkillUnavailableError.retry_after` is currently only ever populated by the
HTTP provider. If a second provider gains transient failures, the backoff loop itself is the
next thing to lift into core — it is provider-agnostic apart from the status-code mapping.

## 8. Structured logging across the SDK

**Labels:** `theme:operability`, `type:feature`, `package:core`, `package:fs`, `package:http`

### Problem

Outside one warning in `validation.py`, the SDK is silent. There is no way to see which skills
were fetched, how long a fetch took, or why a provider fell back — which makes production
support guesswork.

### Proposal

- Module-level loggers under a consistent `agentskills.*` namespace.
- Library attaches **no handlers** and adds `NullHandler`; the host application configures output.
- `DEBUG` for fetch/parse/cache events, `INFO` for registration outcomes, `WARNING` for degraded behaviour.
- A redaction helper applied to anything containing a URL, header, or query string so `Authorization` values and SAS tokens never reach a log record. Pairs with the error messages in issue 7.

### Acceptance criteria

- [ ] Consistent logger namespace, `NullHandler` attached
- [ ] No secret material in any log record (test with a provider configured with a bearer token and a SAS-style query param)
- [ ] Logging conventions documented in `docs/DEVELOPMENT.md`

## 10. Automate PyPI publishing with Trusted Publishing

**Labels:** `theme:project-health`, `type:chore`

### Problem

Releasing means a maintainer running `scripts/publish.ps1` locally with PyPI credentials, in
dependency order, across six packages. It is manual, unauditable, requires a long-lived token
on a workstation, and is easy to get half-done.

### Proposal

GitHub Actions workflow triggered by the release tag, using **PyPI Trusted Publishing** (OIDC,
no stored token):

- Build all six packages
- Publish in dependency order: `core` → providers → integrations
- Gate on a GitHub Environment requiring manual approval
- Dry-run to TestPyPI on release-candidate tags
- Attach build provenance attestations (prerequisite for artifact signing in v1.0)

Keep `publish.ps1` for local/emergency use.

### Acceptance criteria

- [ ] Tag push publishes all six packages with no stored credentials
- [ ] Dependency order enforced; a failure mid-sequence is clearly reported
- [ ] TestPyPI path verified end-to-end
- [ ] Release process in `docs/DEVELOPMENT.md` updated

## 11. Restore compatibility with Agent Framework 1.x

**Labels:** `theme:correctness`, `type:bug`, `package:agentframework`, `package:mcp-server`

### Problem

`agent-framework-core` renamed `BaseContextProvider` to `ContextProvider`. Both integrations
still import the old name:

```python
from agent_framework import BaseContextProvider, FunctionTool
```

Our constraint is `agent-framework-core = ">=1.0.0rc3,<2.0"`, which admits 1.12.1, so a fresh
`pip install agentskills-agentframework` resolves the new version and raises `ImportError` at
import time. **The published 0.2.3 packages are broken for anyone installing today.** CI and
local runs pass only because `poetry.lock` pins 1.0.0rc3.

Confirmed on a clean Python 3.14 environment: 23 failures across
`agentskills-mcp-server/tests/test_context_provider.py`, plus collection errors in both
`agentskills-agentframework` test modules. Every one traces to this rename.

A second defect compounds it. The lazy import in `context_provider.py` catches `ImportError`
and re-raises:

> `AgentSkillsMcpContextProvider requires agent-framework. Install it with: pip install agentskills-mcp-server[agentframework]`

The package *is* installed. The advice is wrong, and it sends the user to reinstall a
dependency they already have instead of revealing the version incompatibility.

### Proposal

- Import `ContextProvider`, falling back to `BaseContextProvider` so both generations work,
  or drop the fallback and raise the floor to the release that introduced the new name.
- Decide the supported range deliberately and encode it. `<2.0` was never verified against
  anything past the release candidate.
- Re-raise the original exception as `__cause__` so the real error survives, and only claim
  the dependency is missing when it genuinely is.
- Add a CI job that resolves dependencies without the lock file, so upstream breaking changes
  surface here rather than in a user's install.

### Acceptance criteria

- [ ] Both integrations import cleanly against `agent-framework-core` 1.12.1
- [ ] Full suite passes on a lock-free install
- [ ] Version constraint reflects the range actually tested
- [ ] The "requires agent-framework" message appears only when the package is absent
- [ ] Unlocked-resolution job added to CI

### Open question

`allow-prereleases` and its `TODO: Remove once a stable 1.0+ is available` are now obsolete —
1.12.1 is stable. Removing the flag belongs with this fix.

## 12. Support Python 3.14

**Labels:** `theme:project-health`, `type:bug`, `package:all`

**Status: merged, awaiting release.**

Every package pinned `python = ">=3.12,<3.14"`, so installation failed outright on current
stable Python. The README attributed this to upstream dependencies; none of them justified it.
`pyyaml`, `httpx`, `langchain-core`, `mcp`, `pydantic`, `pyjwt` and `agent-framework-core` all
declare 3.14 support. The cap was inherited across all six packages, including
`agentskills-core`, whose only dependency is `pyyaml`.

Ceiling raised to `<4.0` rather than removed, because `langchain-core` declares `<4.0.0` and
Poetry requires a project range that is a subset of its dependencies. 3.14 added to the CI
matrix and the classifiers.

Verified on Python 3.14.6: all six packages install, and 265 tests pass. The only failures are
issue 11 above, which is unrelated to the Python version.

The fix has no effect until a release goes out — the `<3.14` cap is baked into the 0.2.3
metadata already on PyPI and cannot be changed retroactively.
